================================================================================
  0. PROJECT PHILOSOPHY & OPERATIONAL MODEL
================================================================================

ZPF is a strictly invitation-only private wealth management portal. There is
no public registration, no "Sign Up" button, and no self-service onboarding.

THE FUNDAMENTAL RULE:
  A client exists in this system ONLY because an admin put them there.
  Every piece of data on a client's account was created or approved by staff.
  The client's portal is a read + request interface — not a self-service bank.

OPERATIONAL FLOW (from first contact to active portal):
  1. Prospective client contacts ZPF via the bank's official email address
  2. Relationship management and due diligence happen offline
  3. Once accepted, an Admin creates the client's account in the admin panel
  4. Admin sets up the client's full portfolio, historical transactions, and assets
  5. Admin generates credentials (ClientID, Passphrase, TOTP enrollment link)
  6. Credentials delivered to client via secure, agreed channel (never email)
  7. Client activates their TOTP authenticator using the enrollment link
  8. Client logs in — their portal is pre-populated with their full portfolio

CLIENT CAPABILITIES (what they can do in the portal):
  - View their portfolio, all asset classes, performance
  - View transaction history and statements
  - Submit transfer/withdrawal requests (admin must approve before execution)
  - Message their assigned admin
  - Upload documents to their vault
  - Change a limited set of personal preferences (see Section 10.14)

WHAT CLIENTS CANNOT DO:
  - Create their own account
  - Add or edit their own financial data
  - Execute transactions without admin approval
  - Change their legal name, DOB, nationality, or other identity fields
  - Change their KYC status
  - Approve their own beneficiaries
  - Reset their own TOTP without admin involvement

================================================================================
  4. CLIENT ACQUISITION & ONBOARDING FLOW
================================================================================

STAGE 1 — INITIAL CONTACT (Offline)
─────────────────────────────────────
  - ZPF publishes a contact email on their public-facing website (e.g., contact@zpfinanz.ch)
    This website is SEPARATE from the portal — it's just an informational page.
  - Prospective client emails or calls ZPF expressing interest
  - Relationship Manager and compliance team conduct offline due diligence:
      - AML screening
      - PEP (Politically Exposed Person) check
      - Source of wealth verification
      - KYC document collection (passport, proof of address, etc.)
  - Decision made: accept or decline client
  - All of this happens entirely outside the portal system

STAGE 2 — ACCOUNT CREATION (Admin Panel)
─────────────────────────────────────────
  Only an Admin (or higher) can create a client account.
  Done via /admin/clients/new (see Section 11.4 for full form spec).

  What admin fills in:
    - Full legal name, display name, date of birth
    - Nationality, domicile country
    - Risk profile, mandate type
    - KYC status (set to VERIFIED after documents checked offline)
    - Assign to self (or another admin if creating on behalf)

  System generates automatically:
    - ClientID: ZPF-XXXX-XXXX (random, unique, checked for collision)
    - Passphrase: 24-char random alphanumeric (admin can optionally override)
    - TOTP enrollment token: signed URL, 72-hour expiry

STAGE 3 — CREDENTIAL DELIVERY (Offline / Secure Channel)
──────────────────────────────────────────────────────────
  Admin downloads or copies three pieces of information:
    1. ClientID (e.g., ZPF-7741-0038) — not secret, but private
    2. Initial Passphrase (shown ONCE in admin panel — admin must note it down)
    3. TOTP Enrollment URL (e.g., auth.zpfinanz.ch/enroll?token=xxxxxxxx)

  These three items are communicated to the client via an agreed secure channel:
    - In-person meeting (preferred)
    - Encrypted document via agreed courier or lawyer
    - NEVER via email in plaintext
    - NEVER via SMS

  [SUGGESTION]: Consider a "Credential Sheet" PDF generated by admin —
  a formatted one-page PDF containing all three items, watermarked with the
  client's name. Admin prints it and hands over physically. The PDF is
  generated in-memory and never stored.

STAGE 4 — TOTP ENROLLMENT (Client Self-Completes)
───────────────────────────────────────────────────
  The enrollment URL (auth.zpfinanz.ch/enroll?token=xxx) is a dedicated page:

  Step 1: Client visits the URL
  Step 2: Page validates the token (must not be expired, must not be used)
  Step 3: Client enters their ClientID (proves they are the right person)
  Step 4: System generates a TOTP secret and displays a QR code
  Step 5: Client scans with any standard authenticator app
           (Google Authenticator, Authy, 1Password, etc.)
  Step 6: Client enters the 6-digit code to confirm enrollment
  Step 7: System stores the TOTP secret (AES-256 encrypted) in the database
  Step 8: Enrollment token is marked as used (one-time use)
  Step 9: System shows 8 backup codes — client writes them down
  Step 10: Redirect: "Your authenticator is set up. You may now log in."

  Important rules:
    - Enrollment token is single-use
    - Enrollment token expires after 72 hours
    - If expired: admin must regenerate (from admin panel)
    - Client cannot re-enroll without admin generating a new token
    - After enrollment, the QR code is gone — it cannot be shown again

STAGE 5 — PORTFOLIO SETUP (Admin)
───────────────────────────────────
  After account creation, admin populates the client's portfolio:
    - Creates asset class entries (monetary, securities, metals, etc.)
    - Enters historical transactions (full history as known)
    - System calculates current values from historical data + current prices
    - Admin reviews totals, confirms they match the client's real-world holdings
  (See Section 8 for the full P&L and historical pricing engine)

STAGE 6 — FIRST LOGIN
───────────────────────
  Client logs in using the 3-step auth flow.
  Their portal is fully pre-populated — not a blank screen.
  Welcome message from RM auto-created in their messages inbox.

  [SUGGESTION]: On first login, show a "Welcome" overlay modal that:
    - Introduces the portal briefly (3 bullet points)
    - Prompts them to change their passphrase (admin set the initial one)
    - Links to their RM card
    - Has a "Got it, take me to my portfolio" dismiss button

================================================================================
  5. AUTHENTICATION SYSTEM
================================================================================

OVERVIEW
────────
  3-factor sequence:
    Factor 1:  ClientID      (identifier — not a secret)
    Factor 2:  Passphrase    (secret — argon2 hash, min 20 chars)
    Factor 3:  TOTP code     (RFC 6238, 30-second, 6-digit)

  No "remember me". No social login. No magic links. No email OTP.

LOGIN FLOW (Step by Step)
──────────────────────────

  STEP 1 — Client Identifier
    UI: Input field formatted ZPF-XXXX-XXXX
    Client-side: regex format validation only
    Server: does NOT confirm if clientId exists (prevents enumeration)
    On submit: advance to step 2, store clientId in component state

  STEP 2 — Passphrase
    UI: password field, show/hide toggle
    POST /api/auth/login { clientId, passphrase }
    Server:
      1. Look up user by clientId
      2. If not found: generate fake argon2 timing delay (prevent timing attacks)
         Return generic error: "Invalid credentials"
      3. If found: verify passphrase against argon2 hash
      4. If wrong: return same generic error "Invalid credentials"
      5. If correct: generate stepToken (JWT, 5 min, signed with APP_SECRET)
         stepToken payload: { userId, step: 'totp', iat, exp }
      6. Return { stepToken }
    Rate limit: 5 attempts per clientId per 10 minutes

  STEP 3 — TOTP Code
    UI: 6 individual digit fields, auto-advance, backspace navigates back
    POST /api/auth/totp/verify { stepToken, code }
    Server:
      1. Validate and decode stepToken (must not be expired)
      2. Retrieve TOTP secret for userId (decrypt from DB)
      3. Verify 6-digit code using otplib (±1 window drift tolerance)
      4. If valid:
          a. Invalidate stepToken (store used tokens in Redis, TTL 5 min)
          b. Create Lucia session in DB
          c. Set session cookie: HttpOnly, Secure, SameSite=Strict
          d. Reset failedTotpAttempts counter to 0
          e. Log login to AuditLog
          f. Update lastLoginAt, lastLoginIp, lastLoginCity on User
          g. Return { success: true }
      5. If invalid:
          a. Increment failedTotpAttempts
          b. If attempts >= 10: lock account (isLocked = true)
             Notify assigned admin via Notification + optional email
          c. Return { error: "Invalid code" }
    Rate limit: 10 attempts per stepToken per 10 minutes

  ON SUCCESS: client.replace('/dashboard/portfolio')
  Admin login: same flow but checks role is not CLIENT, redirects to /admin/overview

SESSION MANAGEMENT
───────────────────
  Library: lucia-auth
  Session stored in PostgreSQL (Session table)
  Cookie name: __zpf_sid (HttpOnly, Secure, SameSite=Strict)
  Idle timeout: 8 hours (reset on each request)
  Absolute timeout: 24 hours
  Multiple sessions allowed (phone + desktop)
  After passphrase change: all sessions revoked immediately

MIDDLEWARE (middleware.ts)
───────────────────────────
  /dashboard/**  → require valid session, role = CLIENT
  /admin/**      → require valid session, role in [ADMIN, MAJOR_ADMIN, SUPER_ADMIN]
  /admin/login   → skip auth check
  /login         → skip auth check
  /              → skip auth check

  On /admin/** routes: attach user's role and adminId to request headers
  so server components can enforce fine-grained permissions.

TOTP RESET (by admin)
──────────────────────
  Client cannot self-reset TOTP.
  Admin generates a new enrollment token → sends new enrollment URL to client.
  Old TOTP secret is NOT deleted until new enrollment is complete.
  On successful new enrollment: old secret replaced, all sessions revoked.

================================================================================
  6. ADMIN HIERARCHY & PERMISSION MODEL
================================================================================

ROLES (in order of authority)
──────────────────────────────

  SUPER_ADMIN
  ───────────
  The single top-level account. Only one should exist in production.
  Created manually via a seed script during initial deployment.
  No one can create or delete a Super Admin through the UI.

  Capabilities:
    - Full access to everything
    - Create / deactivate Major Admins
    - Create / deactivate Admins (assign to a Major Admin)
    - View all clients, all transactions, all messages, all audit logs
    - View all admins' activities and performance
    - Change system configuration
    - Generate system-wide reports
    - Cannot be locked out by any other user

  MAJOR_ADMIN
  ────────────
  Second in command. Typically a senior manager or COO-level role.
  Created by Super Admin only.

  Capabilities:
    - Create Admins (who are assigned to this Major Admin as owner)
    - View all clients under their assigned Admins
    - View all transactions, transfers, messages across their Admins' clients
    - See full activity log of every Admin under them
    - Override or re-assign a client from one Admin to another (within their scope)
    - Approve large transfers that exceed Admin approval threshold
      [SUGGESTION]: Set threshold — e.g., transfers > CHF 500,000 require
      Major Admin counter-approval regardless of which admin initiated it
    - Deactivate Admins under them
    - Cannot create Major Admins
    - Cannot access clients outside their scope (unless Super Admin)

  ADMIN
  ──────
  The operational level. Creates and manages client accounts.
  Created by Super Admin or Major Admin.
  Always assigned to a Major Admin as "parent".

  Capabilities:
    - Create client accounts
    - View and edit clients they own (createdByAdminId = this admin)
    - Set up client portfolios and historical transactions
    - Approve / reject withdrawal requests from their clients
    - Receive and reply to messages from their clients (in-panel)
    - View only their own clients — NOT other admins' clients
    - Upload / manage documents in client vaults
    - Generate statements for their clients
    - Cannot create other admins
    - Cannot see the activity of other admins

OWNERSHIP CHAIN
────────────────
  SuperAdmin
      └── MajorAdmin A
              ├── Admin 1
              │       ├── Client X (createdByAdminId = Admin 1)
              │       └── Client Y
              └── Admin 2
                      └── Client Z

  Rules:
    - Admin 1 can ONLY see Client X and Client Y
    - Major Admin A can see X, Y, and Z (all clients under their admins)
    - Super Admin sees everyone
    - A client CANNOT be shared between admins — one owner at a time
    - [SUGGESTION]: Super Admin can reassign a client to a different admin
      (e.g., if an admin leaves). This creates an AuditLog entry.

DATABASE REPRESENTATION
────────────────────────
  On the User model (for admin accounts):
    role              Role    — ADMIN | MAJOR_ADMIN | SUPER_ADMIN | CLIENT
    parentAdminId     String? — for ADMIN: points to their MajorAdmin's userId
                              — for MAJOR_ADMIN: null (owned by SuperAdmin)
    createdByUserId   String? — who created this account

  On ClientProfile:
    ownerAdminId      String  — the Admin who created and owns this client
    assignedRmId      String? — optional: RM display name shown in portal
                                (can be a different admin or a display-only field)

WHAT EACH ROLE SEES IN ADMIN PANEL
─────────────────────────────────────
  Super Admin sees:  Everything. No filters applied.
  Major Admin sees:  All clients and admins under their tree only.
  Admin sees:        Only their own clients. No other admin's data.
  All roles see:     Their own messages, their own notifications.

PERMISSION ENFORCEMENT
───────────────────────
  lib/permissions.ts exports helper functions:

    canAccessClient(actingUser, clientId): boolean
      — checks ownership chain before returning any client data

    canApproveTransfer(actingUser, transfer): boolean
      — Admin can approve transfers for their clients up to threshold
      — Major Admin can approve above threshold for their scope
      — Super Admin can approve anything

    canManageStaff(actingUser, targetUser): boolean
      — Super Admin can manage anyone
      — Major Admin can manage admins under them only

  All API routes call these helpers before executing any query.
  Return 403 if check fails — do NOT leak that the resource exists.

================================================================================
  7. DATABASE SCHEMA (PRISMA)

================================================================================
  8. HISTORICAL PRICING & P&L CALCULATION ENGINE
================================================================================

This is one of the most important and complex parts of the system.
When an admin adds a historical transaction (e.g., "gold purchase on 2015-03-14"),
the system needs to:
  1. Record the transaction with the price and FX rate at that historical date
  2. Calculate the cost basis (what was paid)
  3. Calculate the current value (using today's price)
  4. Compute P&L = current value - cost basis

PRICE AT HISTORICAL DATE
─────────────────────────
  When admin creates a historical transaction, they MUST supply:
    - transactionDate: the actual date it occurred
    - priceAtDate: the price per unit on that date (in the asset's currency)
    - fxRateAtDate: the FX rate to CHF on that date (if non-CHF asset)
    - amountChf: automatically calculated from above (or manually overridable)

  [SUGGESTION]: In the admin transaction form, provide a "Lookup historical price"
  button per asset type:
    - Metals: query PriceHistory table (pre-populated from metals API)
    - Crypto: query PriceHistory table (pre-populated from CoinGecko history)
    - FX: query PriceHistory table (pre-populated from Frankfurter API history)
    - Securities: must be entered manually (no free historical price API for stocks)
    - Real estate: always manual
  The button auto-fills priceAtDate and fxRateAtDate — admin can override.

PRICE HISTORY PRE-POPULATION
──────────────────────────────
  On first deployment and weekly thereafter (BullMQ job):
    - Metals (XAU, XAG, XPT): fetch 10-year daily history from metals-api.com
    - Crypto (BTC, ETH): fetch full daily history from CoinGecko free API
    - FX (EUR, USD, GBP vs CHF): fetch full daily history from Frankfurter API
  Store in PriceHistory table.

  This means admins entering historical transactions from 2010 onwards
  can auto-fill accurate prices.

P&L RECALCULATION FLOW
────────────────────────
  Triggered when:
    - Admin adds, edits, or deletes an AssetTransaction
    - Daily price update job runs (updates current prices)
    - Admin manually triggers recalculation

  For each AssetClass in the portfolio:
    1. Sum all CREDIT transactions = quantity held, total cost basis in CHF
    2. Subtract all DEBIT transactions (sales, withdrawals)
    3. Fetch current price from PriceCache
    4. currentValue = currentQuantity × currentPrice
    5. unrealisedGain = currentValue - costBasis
    6. unrealisedGainPct = unrealisedGain / costBasis × 100
    7. Update AssetClass.valueChf, AssetClass.trendPct
    8. Update holding model (MetalHolding.totalValueChf, etc.)
    9. Sum all asset class values → Portfolio.totalValueChf
   10. Recalculate Portfolio.allocationPct per asset class
   11. Update Portfolio.lastCalculatedAt

  QUARTERLY CHANGE:
    - Store a PortfolioSnapshot at the end of each quarter (BullMQ cron job)
    - quarterlyChangeChf = currentValue - snapshotValue from 90 days ago
    - If no snapshot exists: show "—" in the UI, don't show incorrect value

  [SUGGESTION — REALISED GAINS]:
  Track sold positions separately:
    - On a DEBIT/SELL transaction: calculate realised gain for that lot
    - Store in a RealisedGain table linked to the transaction
    - Show total realised P&L on the Performance page
    - Important for tax reporting

EXAMPLE: Admin adds gold purchase from 2015
──────────────────────────────────────────
  Admin form input:
    transactionDate: 2015-03-14
    type: METAL_PURCHASE
    metal: GOLD (XAU)
    quantity: 10 troy oz
    [Click "Lookup price"] → system finds XAU/CHF on 2015-03-14 = CHF 1,147.20/oz
    priceAtDate: 1,147.20 (auto-filled, admin can edit)
    amountChf: 11,472.00 (calculated)
    description: "Gold purchase — 10oz, allocated vault, Zürich"

  What gets saved:
    AssetTransaction { transactionDate: 2015-03-14, quantity: 10, priceAtDate: 1147.20,
                       amountChf: 11472.00, type: METAL_PURCHASE, direction: CREDIT }

  After recalculation (assuming today XAU/CHF = 2,400/oz):
    MetalHolding.weightTroyOz = 10
    MetalHolding.spotPriceChf = 2,400.00
    MetalHolding.totalValueChf = 24,000.00
    P&L = 24,000 - 11,472 = +12,528 CHF (+109.2%)

  This is what the client sees: their gold is worth CHF 24,000
  (bought for CHF 11,472 — an unrealised gain of CHF 12,528)

================================================================================
  9. API ARCHITECTURE
================================================================================

All API routes under /api. Next.js Route Handlers.
All routes require authentication via requireSession() helper.
Admin routes additionally require role check via canAccessClient() or equivalent.

RESPONSE FORMAT
────────────────
  Success:  { data: T, meta?: { total, page, limit } }
  Error:    { error: { code: string, message: string } }

RATE LIMITS
────────────
  POST /api/auth/login:              5 per 10 min per clientId
  POST /api/auth/totp/verify:       10 per 10 min per stepToken
  POST /api/transfers:               3 per hour per userId
  POST /api/vault/upload:           10 per day per userId
  All other authenticated routes:  120 per minute per userId

CLIENT ROUTES
──────────────
  GET  /api/auth/session              — get current session user
  POST /api/auth/login                — step 2 (passphrase verify)
  POST /api/auth/totp/verify          — step 3 (TOTP verify)
  POST /api/auth/logout               — invalidate session
  POST /api/auth/change-passphrase    — change passphrase (requires current + TOTP)

  GET  /api/portfolio                 — full portfolio for client
  GET  /api/assets/monetary           — monetary holdings detail
  GET  /api/assets/securities         — securities detail
  GET  /api/assets/metals             — metals detail
  GET  /api/assets/digital            — digital assets detail
  GET  /api/assets/real-estate        — real estate detail

  GET  /api/transfers                 — list client's transfer requests
  POST /api/transfers                 — submit new transfer request
  GET  /api/transfers/[id]            — single transfer detail
  PATCH /api/transfers/[id]/cancel    — cancel pending transfer

  GET  /api/vault                     — list vault documents
  POST /api/vault/upload              — get presigned S3 upload URL
  GET  /api/vault/[docId]             — get document + signed download URL
  PATCH /api/vault/[docId]/confirm    — confirm upload completed

  GET  /api/messages                  — list message threads
  POST /api/messages                  — create new thread
  GET  /api/messages/[threadId]       — get thread with messages
  POST /api/messages/[threadId]       — send a message in thread

  GET  /api/statements                — list statements
  GET  /api/statements/[id]/download  — signed download URL

  GET  /api/notifications             — list + unread count
  PATCH /api/notifications/[id]/read  — mark as read

  GET  /api/beneficiaries             — list beneficiaries
  POST /api/beneficiaries             — propose new beneficiary (pending admin verify)
  PATCH /api/beneficiaries/[id]       — edit nickname (limited — cannot change IBAN)

  SECURITY_ALERT                Unusual login detected   Admin + Super Admin
  BENEFICIARY_PROPOSED          Client proposes          Assigned admin (in-panel)

─────────
  In-portal: badges + topbar banner
  Email: Resend — only when admin has notificationEmail configured

  14. DOCUMENT VAULT ARCHITECTURE
================================================================================

UPLOAD FLOW
────────────
  1. Client (or admin) selects file
  2. App calls POST /api/vault/upload { fileName, mimeType, category }
  3. Server validates auth, file type, size limit
  4. Server creates VaultDocument record (status: PENDING)
  5. Server generates presigned S3 PUT URL (60-second expiry)
  6. Client uploads directly to S3 via presigned URL
  7. Client calls PATCH /api/vault/[docId]/confirm
  8. Server marks document ACTIVE
  9. [SUGGESTION]: BullMQ job scans file with ClamAV before marking ACTIVE.
     Status goes: PENDING → SCANNING → ACTIVE (or QUARANTINED if infected)

DOWNLOAD FLOW
──────────────
  1. Call GET /api/vault/[docId]
  2. Server checks: auth, ownership, not sealed (for client)
  3. Server generates presigned S3 GET URL (60-second expiry)
  4. Creates DocDownloadLog and AuditLog entries
  5. Returns { signedUrl, expiresIn: 60 }
  6. Client opens URL in new tab

S3 STRUCTURE
─────────────
  Bucket: zpf-vault-prod (private, no public access, versioning on, SSE-KMS)
  /vault/[clientId]/[docId]/[filename]
  /message-attachments/[threadId]/[messageId]/[filename]
  /transfer-attachments/[transferId]/[filename]
  /statements/[clientId]/[statementId]/[filename]
  /avatars/[userId]/avatar.[ext]               (if avatar upload enabled)
  Region: eu-central-1 (Frankfurt)

  15. SECURITY INFRASTRUCTURE
================================================================================

TRANSPORT & HEADERS
─────────────────────
  HTTPS only, HSTS with preload.
  All headers set in next.config.ts:

    Strict-Transport-Security:   max-age=31536000; includeSubDomains; preload
    X-Frame-Options:             DENY
    X-Content-Type-Options:      nosniff
    Referrer-Policy:             no-referrer
    Permissions-Policy:          geolocation=(), camera=(), microphone=()
    Cross-Origin-Opener-Policy:  same-origin
    Content-Security-Policy:     (strict, nonce-based for scripts)

APPLICATION-LEVEL ENCRYPTION
──────────────────────────────
  Fields encrypted before storing in DB (AES-256-GCM via Node.js crypto):
    - Beneficiary.iban
    - User.totpSecretEnc
  Storage format: base64(iv + authTag + ciphertext) as a single string
  Key source: TOTP_ENCRYPTION_KEY env variable (32 bytes)
  Key rotation: annually — decrypt all, re-encrypt with new key, update env

RATE LIMITING
──────────────
  All auth endpoints: Upstash Redis sliding window
  /api/auth/login:             5 per 10 min per clientId
  /api/auth/totp/verify:      10 per 10 min per stepToken
  /api/admin/*:               60 per minute per adminId
  All other authenticated:   120 per minute per userId

CSRF
─────
  Next.js App Router server actions: built-in CSRF protection
  API routes: validate Origin/Referer header against allowed origins

SESSION SECURITY
─────────────────
  Cookie: __zpf_sid — HttpOnly, Secure, SameSite=Strict
  Sessions in DB — immediate revocation possible
  After passphrase change: all sessions revoked
  Admin can revoke all sessions for any user from admin panel

INPUT VALIDATION
─────────────────
  Zod schemas on the server for every mutation
  Message body: sanitize with sanitize-html before storing (prevent XSS in admin panel)
  File uploads: validate MIME type AND file header magic bytes (not just extension)

DEPENDENCY SECURITY
─────────────────────
  npm audit on every CI run
  Dependabot enabled
  eslint-plugin-security on all code

SECRETS
────────
  DATABASE_URL, DIRECT_URL, APP_SECRET, TOTP_ENCRYPTION_KEY,
  AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION, S3_BUCKET_NAME,
  UPSTASH_REDIS_REST_URL, UPSTASH_REDIS_REST_TOKEN, RESEND_API_KEY
  All in Vercel Environment Variables — never in code or git

  20. COMPLIANCE & REGULATORY
================================================================================

SWISS DSG / GDPR
─────────────────
  - Privacy policy accessible from login page (before authentication)
  - DSAR: Super Admin can export all personal data for a given client
  - Right to erasure: flagged as not fully possible during retention period
  - Data retention policy: financial records 10 years (Swiss AML Art. 7)
  - Soft delete everywhere (deletedAt field) — hard delete only after retention period

FINMA / AML / KYC
──────────────────
  - KYC status tracked per client (verified date, expiry date)
  - KYC expiry alerts to admin 30 days before (Notification + email)
  - Beneficial ownership captured (nationality, domicile)
  - PEP flag per client (manual admin field)
  - AML notes per client (admin-only text)
  - Source of wealth notes (admin-only)
  - All financial transactions logged with date, amount, counterparty
  - Transfer approvals: segregation of duties enforced (client submits, admin approves)
  - Large transfers: require counter-approval (Major Admin or Super Admin)

AUDIT TRAIL IMMUTABILITY
─────────────────────────
  Postgres Row Level Security on audit_logs:
    REVOKE UPDATE, DELETE ON audit_logs FROM application_user;
  Only INSERT allowed from application.
  AuditLog records include: userId, action, entityType, entityId, IP, timestamp, metadata.

RECORD RETENTION
─────────────────
  No hard delete on: VaultDocument, AssetTransaction, Activity, AuditLog, Message
  All use soft delete (deletedAt) or archival
  After retention period (10 years): authorised Super Admin can permanently purge,
  with a final AuditLog entry recording the purge

     ClientID, Passphrase, and TOTP enrollment link to new clients?

     historical stock prices. Will admin enter these manually, or do you

     come from? Suggest: noreply@zpfinanz.ch (requires DNS setup for Resend).

     be tracked separately and shown on the performance page? Important for
     client tax reporting.

     phone number (pending admin approval), or is this fully admin-managed?

  7. MULTI-CURRENCY PORTFOLIO DISPLAY: When client changes preferred
     currency from CHF to USD, should all values be live-converted at
     current FX rates, or shown with a "converted at [date] rate" note?
