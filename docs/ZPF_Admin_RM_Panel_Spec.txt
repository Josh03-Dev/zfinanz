OVERVIEW
================================================================================

The Admin (RM) is the ground-level operator of the ZPF platform. Every client
account they manage was created by them or assigned to them. They are the
client's Relationship Manager — the face of ZPF to that client.

CORE RESPONSIBILITIES:
  - Create client accounts (full identity, credentials, onboarding date)
  - Build and maintain each client's complete portfolio history
  - Enter all asset data and historical transactions (backdated to any date)
  - Approve/reject withdrawal and transfer requests from their clients
  - Message clients via the secure in-portal system (+ optional email delivery)
  - Generate statements and upload documents to client vaults
  - Monitor KYC expiry, document review dates, and account health
  - Communicate internally with the wider ZPF team (departments)

DATA SCOPE:
  An Admin can only see and act on clients where ownerAdminId = their userId.
  Attempting to access another admin's client returns 403 — no data leakage.

NOTE ON RM DISPLAY:
  The client's portal shows an RM card with a name, title, initials, phone,
  and availability. By default this auto-populates from the Admin's StaffProfile.
  An optional override exists per-client (ClientProfile.rmDisplay* fields) —
  useful when the firm wants to display a senior partner's name even if a
  junior admin handles day-to-day operations.

DEPARTMENT MODEL:
  ZPF operates multiple internal departments, each with their own portal login
  and messaging capability. The RM (Admin) is not the only party who can contact
  a client. Departments communicate independently:
    - Relationship Manager (RM)     → day-to-day portfolio and advisory
    - Compliance                    → KYC, FATCA/CRS, regulatory notices
    - Operations                    → transfer confirmations, settlement notices
    - Custody & Vault               → metals audit, document custody confirmations
    - Advisory / Research           → market notes, rebalancing recommendations
    - [SUGGESTION] Tax Desk         → tax planning notes, reporting documents
    - [SUGGESTION] Legal            → legal correspondence, trust/estate matters
  Each department has its own portal (login, inbox, compose) and their messages
  appear in the client's portal under the relevant category badge.
  See Section 7 (Department Portal) for the full spec.

2. CLIENT ACCOUNT CREATION (/admin/clients/new)
================================================================================

The RM creates every client account. Nothing about a client can come from
the client themselves at this stage — the RM builds the full picture.

────────────────────────────────────────────────────────────────────────────────
MULTI-STEP CREATION FORM
────────────────────────────────────────────────────────────────────────────────

STEP 1 — IDENTITY
──────────────────
  Full legal name (required)
  Display name (pre-filled, editable — e.g., "Adebayo S.")
  Initials (auto-generated, editable — "AS")
  Date of birth
  Nationality (country select)
  Domicile country (country select)
  Phone number (optional)

STEP 2 — ACCOUNT SETTINGS & HISTORICAL DATE
─────────────────────────────────────────────
  Account creation date:
    Default: today
    Override: [date picker — can be any past date]
    Use case: client has been a ZPF client since 2015 but we are now
              migrating them onto the portal. Set onboardedAt = 2015-06-01.
    This date is what appears in the client portal as "Member since [date]"
    and what the performance/analytics engine uses as the "Since Inception"
    start point.
    Note field: "Reason for backdating (internal only)" — logged in AuditLog.

  Risk profile:    Conservative / Balanced / Growth / Aggressive
  Mandate type:    Advisory / Discretionary / Execution Only
  Mandate date:    [date picker] — when mandate was agreed (can be backdated)

  KYC status:      Default: VERIFIED (due diligence done offline)
  KYC verified date: [date picker] (can be backdated)
  KYC expiry date: [date picker, optional]

STEP 3 — RM DISPLAY INFORMATION
─────────────────────────────────
  What the client sees in their portal as their "Relationship Manager" card.
  Default: auto-populate from this RM's own StaffProfile
  Override option: "Use custom display" toggle → allows entry of different:
    RM Display Name (e.g., "Dr. Markus von Steiner")
    RM Title
    RM Initials
    RM Phone
    RM Availability message (e.g., "Available — responds within 4 hours")
    RM Next Call (date/time picker, optional)
  Use case: senior partner shown to client while junior RM does the work.

STEP 4 — CUSTODIAN DISPLAY
────────────────────────────
  What appears in the client's portfolio as the custodian line:
    Custodian name (default: "ZPF AG — Primary Custody")
    Custodian address (default: "Bahnhofstrasse 72, 8001 Zürich")
  These are display fields — they don't affect backend logic.

STEP 5 — CREDENTIALS PREVIEW
──────────────────────────────
  System generates and shows:
    ClientID:        ZPF-XXXX-XXXX (auto-generated, unique, shown for the first time)
    Initial Passphrase: [24-char random alphanumeric] (shown ONCE — cannot be retrieved)
    TOTP Enrollment URL: auth.zpfinanz.ch/enroll?token=xxxxx (72hr expiry)

  "Download Credential Sheet" button:
    Generates a one-page PDF in-memory (never stored to DB or S3):
      - Client name + ClientID
      - Passphrase (clearly labelled "Change after first login")
      - TOTP enrollment URL + QR code
      - ZPF branding + watermark with client name
    Admin prints and hands over physically or seals in envelope.

  "I have securely noted these credentials" checkbox (required to proceed)

STEP 6 — CONFIRM & CREATE
───────────────────────────
  Summary of all entered data
  "Create Client Account" submit

  On creation:
    → ClientProfile, Portfolio, AssetClasses (empty) created
    → TotpEnrollmentToken generated
    → Welcome message auto-sent in client's RM thread:
        "Welcome to ZPF Private Client Portal. Your account has been set up
         and your portfolio will be available shortly. Please complete your
         TOTP authenticator setup using the link provided."
    → AuditLog: CLIENT_CREATED (includes backdated onboardedAt if applicable)

3. PORTFOLIO & ASSET MANAGEMENT
================================================================================

This is the RM's primary operational task after creating a client. All of a
client's financial data — past and present — is entered by the RM.

────────────────────────────────────────────────────────────────────────────────
PORTFOLIO VIEW (/admin/clients/[clientId]/portfolio)
────────────────────────────────────────────────────────────────────────────────

  Layout: mirrors what the client sees (portfolio overview page) but with
  admin overlays — every section has an [Edit] or [+ Add] control.

  Shows:
    Portfolio hero card (total AUM, quarterly change, unrealised gain)
    Asset class cards (6): each with [Edit Display Settings] + [Add Transaction]
    Allocation bar
    Recent transactions (last 10)
    [Force Recalculate P&L] button (triggers recalc job immediately)
    Last calculated at: [timestamp]

  [Edit Display Settings] on any asset class card:
    → Modal to edit the card's display label, subline, color (cosmetic only)

────────────────────────────────────────────────────────────────────────────────
ASSET CLASS SETUP
────────────────────────────────────────────────────────────────────────────────

  Each client has 6 asset class slots (MONETARY, SECURITIES, PRECIOUS_METALS,
  DIGITAL_ASSETS, REAL_ESTATE, DOCUMENT_VAULT).
  All created empty on account creation — RM populates them.

  Before entering transactions, RM creates the specific holdings within each
  asset class. Holding creation can be done inline in the transaction form
  or via a dedicated "Manage Holdings" view per asset class.

  MONETARY HOLDINGS — add per currency account:
    Currency (select)
    Account type (Current Account / Notice Account / Fixed Term / Savings)
    Masked account number (e.g., CH56 0483 •••• •••• 7800 0)
    Interest rate (% p.a.)
    Account opened date [backdatable date picker]
    Maturity date (if fixed term)
    Notice period (if notice account)

  SECURITIES — add per position:
    Ticker / ISIN
    Security name
    Security type (Equity / Bond / ETF / Fund / Structured Product)
    Exchange
    Currency
    For bonds: coupon rate, maturity date

  PRECIOUS METALS — add per holding/bar:
    Metal type (Gold / Silver / Platinum / Palladium)
    Weight (troy oz)
    Bar description (e.g., "3 × 400oz Good Delivery Bars")
    Vault location (text + optional vault ID)
    Fineness (e.g., 999.9)
    Bar reference(s)
    Acquisition date [backdatable]
    Insurance details (optional)

  DIGITAL ASSETS — add per coin:
    Ticker (BTC, ETH, etc.)
    Name
    Custody type / provider
    Wallet reference (masked)

  REAL ESTATE — add per property:
    Property name
    Address + country
    Property type (Residential / Commercial / Land / Other)
    Acquisition date [backdatable]
    Acquisition cost (CHF)
    Last valuation (CHF) + valuation date
    Valuation status (Active / Pending)
    Title document reference (links to vault document)
    Encumbrances (text)

────────────────────────────────────────────────────────────────────────────────
TRANSACTION ENTRY (/admin/clients/[clientId]/transactions — "Add Transaction")
────────────────────────────────────────────────────────────────────────────────

  The transaction form is the core data-entry surface. Every balance, cost
  basis, and P&L figure the client sees is derived from transactions entered here.

  FULLY BACKDATABLE:
    Every transaction can be set to any past date. There is no "minimum date"
    restriction. A client onboarded today might have transactions going back
    to 2008. The RM enters the full history as known.
    The system recalculates P&L from the earliest transaction forward.

  FORM FIELDS:
  ─────────────

  Asset Class:        [select from client's 6 asset classes]

  Specific Holding:   [select from holdings within that class]
                      + "New Holding" option → inline holding creation form

  Transaction Type:   [dropdown — options depend on selected asset class]
    MONETARY:         Wire In / Wire Out / Interest Credit / Fee Debit / FX Conversion
    SECURITIES:       Security Buy / Security Sell / Dividend / Coupon Payment
    PRECIOUS METALS:  Metal Purchase / Metal Sale / Transfer In / Transfer Out
    DIGITAL ASSETS:   Crypto Buy / Crypto Sell / Transfer In / Transfer Out
    REAL ESTATE:      Property Acquisition / Property Sale / Rental Income
    GENERIC:          Manual Adjustment

  Direction:          [CREDIT or DEBIT — auto-set from type, overridable]

  Transaction Date:   [date picker — any past date, no floor]
    Hint text: "Use the actual date the transaction occurred, not today's date."
    If date > 1 year ago: show subtle notice:
      "This is a historical entry — backdating to [selected date]."

  Quantity:           [number — troy oz, shares, BTC, etc. — shown if applicable]

  Price at Date:      [number — price per unit in the asset's native currency]
    [Look Up Historical Price] button:
      For metals (XAU/XAG/XPT): queries PriceHistory table for selected date
      For crypto (BTC/ETH): queries PriceHistory table for selected date
      For FX: queries PriceHistory table for selected date
      For securities: manual only (no free historical data API)
      For real estate: manual only
      Auto-fills the field — RM can accept or override.

  FX Rate at Date:    [number, shown if non-CHF asset]
    [Look Up Rate] button: queries PriceHistory for selected date
    Auto-fills EUR/CHF, USD/CHF, GBP/CHF, etc.

  Amount (Native):    [auto-calculated: quantity × priceAtDate]
                      [overridable — unlock with warning]

  Amount (CHF):       [auto-calculated: amountNative × fxRateAtDate]
                      [overridable — unlock with warning]

  Description:        [text — internal admin label]
    Examples: "Gold purchase — 5oz, LBMA delivery, Zürich vault"
              "Wire in from Standard Chartered Lagos — Q3 contribution"

  Client Activity Label: [text — what the client sees in their activity feed]
    Default: same as description
    Can be different: admin might write "Portfolio contribution" instead of
    the full SWIFT details.
    Examples: "Inbound wire — CHF account · Verified & credited"
              "Gold purchase — 5oz allocated"

  Show in Client Activity: [checkbox, default: checked]
    Uncheck for internal/adjustment entries not meant for client visibility.

  Reference:          [optional — bank ref, SWIFT ref, trade ID, etc.]

  Internal Notes:     [optional text — admin-only, never shown to client]

  SAVE BEHAVIOUR:
    → POST /api/admin/clients/[clientId]/transactions
    → P&L recalculation triggered asynchronously (BullMQ)
    → Dashboard shows "Recalculating portfolio…" spinner
    → On completion: all computed values update
    → AuditLog: TRANSACTION_ADDED

  EDITING TRANSACTIONS:
    → Any historical transaction can be edited (correcting data entry errors)
    → Edit captures before/after snapshot in AuditLog: TRANSACTION_EDITED
    → P&L recalculated after edit

  DELETING TRANSACTIONS:
    → Soft delete (deletedAt field, excluded from calculations)
    → Requires confirmation: "This will affect the client's portfolio balance.
       The transaction will remain in the audit log as deleted."
    → AuditLog: TRANSACTION_DELETED

  BULK IMPORT [SUGGESTION]:
    For new clients being migrated with years of history, provide a CSV import:
      - Template downloadable from the form
      - Columns: date, assetClass, holdingRef, type, direction, quantity,
                 priceAtDate, fxRateAtDate, amountNative, amountCHF,
                 description, clientLabel, reference
      - Server validates each row before committing
      - On validation errors: show row-by-row error list, do not commit partial
      - On success: commit all rows, trigger one recalculation job
    This makes migrating a client with 10 years of transaction history
    practical without manually entering 200+ rows.

────────────────────────────────────────────────────────────────────────────────
TRANSACTION LIST VIEW (/admin/clients/[clientId]/transactions)
────────────────────────────────────────────────────────────────────────────────

  Same visual style as client's transactions page but with admin controls.

  Filters: Asset Class · Transaction Type · Direction · Date Range
  Search: by description, reference, or amount

  Each row shows:
    Date (actual transaction date, not entry date)
    Type badge
    Description (admin label)
    Amount (native + CHF)
    P&L impact indicator (small green/red delta)
    Entered by (admin name)
    Entry date (when it was entered — different from transaction date)
    [Edit] [Delete] actions

  Summary strip:
    Total credits | Total debits | Net flow | Earliest transaction date

  [+ Add Transaction] button always visible top-right.

────────────────────────────────────────────────────────────────────────────────
TRANSFER LIST
────────────────────────────────────────────────────────────────────────────────

  Tabs: Pending (default) / Under Review / Approved / Executed / Rejected / All
  Filter by client (dropdown — my clients only)

  Each transfer card shows:
    Client name + ClientID
    Amount: [currency] [amount] (≈ CHF equivalent)
    Beneficiary: full name | country | masked IBAN
    Bank: bank name | BIC
    Reference
    Category badge (Personal / Investment / Operating / etc.)
    Client notes
    Submitted date/time
    Attachments

  Action buttons:
    [Begin Review]    → status: UNDER_REVIEW
    [Approve]         → if ≤ threshold: status: APPROVED, client notified
                        if > threshold: status: AWAITING_COUNTER (Major Admin notified)
                        [SUGGESTION]: Show CHF equivalent prominently to avoid
                        mistakes on FX transfers. E.g., "GBP 85,000 ≈ CHF 97,240"
    [Reject]          → requires rejection reason [textarea]
                        Client notified in-portal + reason shown
    [Request Clarification] → opens message thread with client (RM channel)
    [Mark Executed]   → enter settlement reference + value date
                        → creates Activity on client account
                        → client notified: "Your transfer has been executed"

  After APPROVED (waiting for execution):
    [Mark Executed] is the only active button
    Shows: "Approved [date] · Awaiting execution"

  BENEFICIARY VERIFICATION (within transfer flow):
    If a client proposed a new beneficiary (isVerified = false),
    the transfer using it will show a "UNVERIFIED BENEFICIARY" warning banner.
    RM must verify the beneficiary before they can approve the transfer.
    [Verify Beneficiary] button opens inline:
      Shows: full name, IBAN, BIC, bank, country
      RM confirms they've verified via agreed process (AML screening, etc.)
      [Mark Verified] → isVerified = true, AuditLog: BENEFICIARY_VERIFIED

6. MESSAGING (/admin/messages)
================================================================================

This is one of the most important sections. The RM is the primary contact
for every client, but multiple ZPF departments can also message clients.

────────────────────────────────────────────────────────────────────────────────
RM MESSAGE INBOX (/admin/messages)
────────────────────────────────────────────────────────────────────────────────

  Layout: Split panel (thread list left, conversation right)

  Thread list shows:
    Filter: All / Unread / Open / Resolved
    Search by client name

    Each row:
      Client display name + ClientID
      Thread subject + category label badge
      Last message preview + timestamp
      Unread dot if unread

  The RM inbox shows threads where:
    category = 'rm' OR category = 'advisory'
    AND assignedAdminId = this RM's userId

  Department threads (compliance, operations, custody, tax, legal) are managed
  by their respective department portals — not by the RM inbox.
  The RM can still VIEW all their client's threads (read-only) from the
  client profile → messages sub-tab. But they compose only in their own channel.

────────────────────────────────────────────────────────────────────────────────
COMPOSING A MESSAGE TO CLIENT
────────────────────────────────────────────────────────────────────────────────

  From: RM inbox → [+ New Message] or from client profile → [Send Message]

  COMPOSE FORM:
    Client:          [pre-filled if coming from client profile]
    Category:        rm (default for RM messages) / advisory
    Subject:         [text input]
    Message body:    Rich text editor (Tiptap)
                     Supports: bold, italic, lists, links, horizontal rule
    Attachments:     Upload up to 3 files (stored in S3)
                     Max 10MB per file, allowed: PDF, DOCX, XLSX, PNG, JPG
    Internal note:   [toggle] — if ON, message is staff-only (not shown to client)
                     Used for internal memos, handover notes, etc.

  EMAIL DELIVERY OPTION:
    □ Also send email notification to client
      When checked:
        - System sends email via Resend to client's email address on file
          (StaffProfile.notificationEmail or ClientProfile.emailAddress)
          [SUGGESTION]: add emailAddress to ClientProfile — a verified email
          field the RM enters during onboarding for email delivery purposes.
        - Email content:
            From:    noreply@zpfinanz.ch (or department-specific alias)
            To:      [client email]
            Subject: "New message from ZPF — [thread subject]"
            Body:    Plain text summary:
                       "Dear [Display Name],
                        You have a new message from [RM Name] at
                        ZPF Privat Finanz AG regarding: [Subject].
                        Please log in to your portal to read and respond.
                        [Portal URL]
                        This message was sent securely via the ZPF client portal.
                        Do not reply to this email."
            IMPORTANT: Never include the actual message content in the email.
                       Email is notification-only — full content only in portal.
        - emailSentAt timestamp stored on the Message record
        - Delivery status tracked (sent / bounced via Resend webhooks)
      When unchecked:
        - In-portal notification only
        - Client sees unread badge on their messages page

  [SUGGESTION] EMAIL ADDRESS ON CLIENT PROFILE:
    Add to ClientProfile:
      emailAddress          String?   — client's email, entered by RM
      emailVerified         Boolean   — admin marks as verified (cannot self-verify)
      emailVerifiedAt       DateTime?
    This field is used ONLY for outbound notifications from bank to client.
    Client never logs in via email — email is one-way notification only.
    RM enters this during onboarding or later from client profile [Edit].

THREAD VIEW (conversation with client)

7. DEPARTMENT PORTAL SYSTEM
================================================================================

This is a major architectural feature. ZPF is not just one person (the RM)
communicating with clients. Multiple internal departments correspond with
clients independently. Each department:
  - Has its own portal login (separate from RM admin login)
  - Has its own inbox of client threads
  - Can initiate messages to clients
  - Can reply to client replies
  - Messages appear in the client's portal under the correct category badge
  - Can optionally send email notifications to clients

8. DOCUMENT MANAGEMENT (/admin/clients/[clientId]/documents)
================================================================================

────────────────────────────────────────────────────────────────────────────────
DOCUMENT LIST (admin view)
────────────────────────────────────────────────────────────────────────────────

  Same list as client sees, plus admin-only columns and actions:

  Columns:
    Icon | Name | Category | Status | Date Lodged | Storage | Review Due | Actions

  Admin Actions per document:
    [Seal]         → client can no longer download; shown as locked with "Sealed" badge
    [Unseal]       → restores client download access
    [Set Review Due Date] → date picker; creates alert for RM at 30-day warning
    [Mark Review Complete] → enter review notes, clears overdue status
    [Edit Metadata] → change category, jurisdiction, description, notes
    [Upload New Version] → replaces current with new S3 upload (keeps old in audit)
    [Lodge Document] → upload on behalf of client (RM lodges docs to vault)
    [Soft Delete]  → requires reason; document retained in audit log, hidden from client

  [+ Lodge Document] button:
    File upload (presigned S3):
      Category (select: corporate / property / succession / legal / financial /
                        kyc_aml / advisory / operations)
      Name
      Description
      Jurisdiction
      Reference number (auto-generated or custom)
      Storage type (physical / digital / both)
      Related asset (optional link to AssetClass or specific holding)
      Review due date (optional)
      Notes (internal)
    After upload:
      → VaultDocument created (status: ACTIVE)
      → Client notified: "A new document has been lodged in your vault"
      → AuditLog: DOCUMENT_UPLOADED

  SEALED DOCUMENTS:
    Sealed docs are visible in the client's vault list (they can see the name/meta)
    but have no download button — replaced with a lock icon and "Sealed" badge.
    Use cases: wills, sealed envelopes, legally restricted documents.
    Unsealing requires the same admin (or higher) to explicitly unseal.

    WHERE userId = this RM's userId
